Why is Postfix not delivering? Diagnosing stuck mail with postsleuth

2026-10-12 · postsleuth v0.1.0 中文版

The queue is growing, users say mail to Gmail "didn't arrive", and mailq prints a wall of text. This walkthrough shows how to get from that wall to a cause and a next step with postsleuth, a read-only CLI (and MCP server) for Postfix.

Where the output comes from: sections 1–5 run postsleuth v0.1.0 against the fixture in the repository (testdata/queue.json and testdata/mail.log, generated by testdata/gen.py to look like a small outbound relay on a bad day; domains and IPs are documentation ranges). The "real Postfix" section is copied from the project's CI log, where a throwaway Postfix 3.7 runs in Docker. Nothing below was edited apart from removing colour.

The usual loop

Diagnosing stuck Postfix mail by hand usually goes: mailq | less, pick a reason that looks common, grep the mail log for it, count with sort | uniq -c (which fails because every line has a different address and IP), run qshape to see whether it is new or old, then dig TXT records for SPF and DMARC. postsleuth does the same reads (postqueue -j, the mail log, DNS) and does the grouping for you. It never changes the queue unless you start it with --allow-mutations.

go install github.com/Blackman99/postsleuth/cmd/postsleuth@latest
# or a static binary from GitHub Releases

1. Group the queue by reason

On the mail host you would run postsleuth queue. Here we feed it the saved postqueue -j output:

postsleuth queue --queue-file testdata/queue.json
QUEUE   212 messages · deferred 205 · active 6 · hold 1 · oldest 1d23h (F5EC72BA69)
  ✗  150  rate_limit        gmail.com, googlemail.com
         421-4.7.28 Gmail has detected an unusual rate of unsolicited mail originating from your IP addr…
         → The receiver is throttling you: lower smtp_destination_concurrency_limit / add
           smtp_destination_rate_delay for that domain, and check your sending reputation.
  ✗   34  blocklist         hotmail.com, outlook.com
         550 5.7.1 Unfortunately, messages from [ip] weren't sent. Please contact your Internet service …
         → The receiver rejects your IP or domain because of a blocklist entry: look the IP up (Spamhaus,
           Microsoft SNDS) and request delisting after fixing the cause.
  ✗   14  timeout           oldcorp.example
         connect to mx.oldcorp.example[ip]: Connection timed out
         → Connections to port 25 time out: many providers block outbound port 25, so test with nc -vz MX 25
           and use a relayhost if blocked.
  ✗    4  dns               acme-typo.example
         Host or domain name not found. Name service error for name=acme-typo.example type=MX: Host not …
         → DNS lookup for the destination failed: check the domain exists and has MX/A records, and that this
           server's resolver works (dig MX domain).
  !    3  greylisting       smallbiz.example
         450 4.7.1 <addr>: Recipient address rejected: Greylisted, see http://postgrey.schweikert.ch/hel…
         → Greylisting: normal, Postfix retries automatically. Only a problem if it persists for hours.

212 messages become five lines. Addresses, IPs and tracking IDs are stripped from each delay reason before grouping, so 150 Gmail deferrals that differ only by recipient collapse into one rate_limit group. Each group gets a category (there are 17, from rate_limit and blocklist to ptr, auth and tls) and a hint. Greylisting is a warning (!), not a problem (✗): Postfix will retry it by itself.

To see the actual messages behind a group, filter by category:

postsleuth queue --queue-file testdata/queue.json --category blocklist --list --limit 1
78715BBD26 deferred 20h6m   85428  billing@example.com
    → j.smith141@hotmail.com
      host outlook-com.olc.protection.outlook.com[52.101.42.3] said: 550 5.7.1 Unfortunately, messages from [203.0.113.7] weren't sent. Please contact your Internet service provider since part of their network is on our block list (S3150). (in reply to MAIL FROM command)

The full reply is kept in --list: Microsoft's S3150 code names the reason (the sending IP is on their block list), which is the thing to search for or paste into a ticket.

2. Since when? (qshape)

postsleuth shape --queue-file testdata/queue.json
SHAPE   deferred queue by recipient domain, age in minutes
                         T     5    10    20    40    80   160   320   640  1280 1280+
              TOTAL    205     0     0     0     9    22    45    80    12    21    16
          gmail.com    141     0     0     0     7    19    39    73     3     0     0
        outlook.com     23     0     0     0     0     0     1     4     6     8     4
    oldcorp.example     14     0     0     0     0     0     0     0     1     5     8
        hotmail.com     11     0     0     0     0     0     0     1     2     6     2
     googlemail.com      9     0     0     0     0     2     5     2     0     0     0
  acme-typo.example      4     0     0     0     0     0     0     0     0     2     2
   smallbiz.example      3     0     0     0     2     1     0     0     0     0     0

Columns are message age in minutes, as in Postfix's qshape. Read it left to right: Gmail's deferrals fill the 40 to 640 minute columns and nothing older, so the throttling started within the last eleven hours or so and new mail is still being caught by it. oldcorp.example is all in the right-hand columns: that destination has been unreachable for most of a day, and those messages will expire at maximal_queue_lifetime unless something changes. Run shape --by sender when you suspect one compromised account is flooding the queue; in this fixture every message comes from example.com, so it doesn't apply.

3. What the log says

The queue only shows what is still stuck. The log shows what already happened, including bounces and mail that was delivered:

postsleuth log --log testdata/mail.log --since all

  ! still failing: gmail.com (82), outlook.com (38), oldcorp.example (5)
  ✗ bounce     14  blocklist         550 5.7.1 Unfortunately, messages from [ip] weren't sent. Please cont… · outlook.com
  ✗ bounce     12  recipient_unknown 554 5.1.1 <addr>: Recipient address rejected: User unknown · yahoo.com
  ✗ deferral   82  rate_limit        421-4.7.28 Gmail has detected an unusual rate of unsolicited mail ori… · gmail.com
  ✗ deferral   38  blocklist         550 5.7.1 Unfortunately, messages from [ip] weren't sent. Please cont… · outlook.com
  ✗ deferral    5  timeout           connect to mx.oldcorp.example[ip]: Connection timed out · oldcorp.example
  ✗ reject     30  relay_denied      554 5.7.1 <addr>: Relay access denied

  domain                             sent  deferred  bounced  last
  gmail.com                           355        82        0  deferred
  outlook.com                          30        38       14  deferred
  yahoo.com                            91         0       12  sent
  oldcorp.example                       0         5        0  deferred
  fastmail.com                        103         0        0  sent
  proton.me                            97         0        0  sent
  qq.com                               90         0        0  sent
  example.com                          26         0        0  sent

Two things the queue could not tell us. First, Gmail is still accepting most mail (355 sent against 82 deferred attempts), which fits rate limiting by volume rather than a hard block. Second, Outlook has bounced 14 messages outright and its last attempt was a deferral: the blocklist is costing real mail. The 30 relay_denied rejects are smtpd refusing outside clients that tried to relay, which is the server doing its job, but a sudden jump in that number is worth noticing.

On a real host, leave out --log: postsleuth reads maillog_file from postconf, then /var/log/mail.log or /var/log/maillog, then journald. Syslog, RFC 3339 and journald timestamps and .gz rotations all work.

5. All of it at once

postsleuth doctor prints the queue summary, the qshape, the log summary and the DNS checks for your sending domain (MX, SPF with its 10-lookup limit, DKIM, DMARC, PTR/FCrDNS), then a result line. It exits 1 when it finds a problem, so it can run from cron or a monitoring check. DNS is skipped here because the fixture's domains are not real:

postsleuth doctor --queue-file testdata/queue.json --log testdata/mail.log --since all --no-dns
echo $?   # 1

The output is sections 1–3 in one report, ending with:

RESULT  6 problem(s), 4 warning(s)

The same run then checks that delete without --allow-mutations and delete ALL are both refused.

Acting on it

The categories map to different fixes, and most of them are not "flush the queue":

  • rate_limit (Gmail 4.7.28): don't flush. A burst of retries makes it worse. Lower smtp_destination_concurrency_limit or add a smtp_destination_rate_delay for that transport, check SPF/DKIM/DMARC alignment and what triggered the volume, then let backoff work.
  • blocklist (Outlook S3150): the IP has a reputation problem. Fix the cause first (open relay, compromised account, missing PTR), then use Microsoft's delisting form and SNDS.
  • timeout: test nc -vz <mx> 25 from the host. Many clouds block outbound port 25; if so, use a relayhost.
  • dns: usually a typo in the recipient domain; tell the sender rather than waiting for the queue lifetime.

When you do need to change the queue, the commands exist but stay locked until you ask for them:

$ postsleuth delete 78715BBD26
postsleuth: delete changes the mail queue; re-run with --allow-mutations if you mean it
$ postsleuth delete ALL --allow-mutations
postsleuth: invalid queue ID "ALL"

For AI agents

postsleuth mcp exposes the same reads as MCP tools over stdio, so Claude, Cursor or another MCP client can answer "why is mail to Outlook stuck?" on a host you point it at (locally, over --wrap "ssh mx sudo", or into a container). The queue-changing tools are not even listed unless the server is started with --allow-mutations, and each call then needs confirm: true. Setup snippets are in the docs.

If postsleuth puts one of your real deferral texts in category other, please open an issue with the text (addresses removed). That is how the classifier gets better.
